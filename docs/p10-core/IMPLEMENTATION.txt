Schema and operation
A canonical personnelPools table (30_物理人员池.csv) owns poolId, display name,
finite positive integer total headcount, explicit enable/shared flags, capacity source,
global scope *, effective timestamp and a reserved handover field. personnelGroups adds
poolId; original group headcount remains a separate qualification ceiling. No name/skill/
shift inference, automatic pool creation, zero/infinite capacities or site defaults.
Use Data & CSV -> physical pools, add a row; edit group mappings on the group tab;
save both drafts together with a reason. Drafts can be incomplete only while disabled.
Once any pool is enabled all groups require explicit known mappings. Referenced disabled/
future pools block supported new runs until configured/effective. Empty handover is not
approval of a 'no handover' business mode; scenes requiring handover cannot use this core.
A saved physical contract cannot be silently stripped back to legacy group semantics.
Deleted IDs are retired from trusted audit history and cannot be reused; name changes
preserve identity. Removal with dangling group references rejects the entire mutation;
a complete remap and deletion in one transaction is allowed.
Both CSV preview/commit and React edits use existing atomic revision/audit/history guards.
Single legacy group CSV can omit poolId before adoption; after adoption, replacing groups
without mapping correctly fails rather than losing the physical constraint.

Execution and independent verification
Existing same-post max/different-post sum, candidate allocation, skills, directed skill
substitution, shift, availability and group headcount continue. Every allocation also
checks aggregate use of all groups mapped to the same pool at every half-open boundary.
Pool membership is derived from frozen groups, including existing reservations; a ledger
label cannot create capacity. A failed candidate never commits any allocations. Existing
bounded search limits remain explicit and do not claim global infeasibility.
New inputs and runs freeze pool table, group mappings and policy fingerprint, with
personnelPoolContract=P10-core-v1. Retry retains original inputs and evaluation instant.
Independent verifier reconstructs demand and windows, then independently sweeps frozen
pool membership and headcount; it does not invoke the allocator. It detects missing/
shortened allocations, forged pool labels, demand changes and excess aggregate use.
Saved resource load adds a separate physical-pool aggregate, alongside group qualification
views. It derives membership from frozen input. Independent posts are not deduplicated
just because their group/quantity/window match. Conflict geometry identifies the pool,
tasks, members, half-open segment, demand, capacity and gap; exports retain frozen input.

Compatibility, risk and rollback
No stored old run/input/plan/confirmation/audit is migrated. Current-state reads expose an
empty new table for maintenance only. Old frozen snapshots without pool configuration keep
their exact old contract; they are not certified as P10. The upgrade probe generates an
actual confirmed store using exact e0be9b6 software, opens that raw store with new code,
then saves new configuration and checks history equality. Missing confirmed input blocks
new saves. Old software rejects new table and mapping fields atomically (404/400).
Rollback is an operational stop of new P10 writes and read-only retention of their stores;
do not strip fields or reopen a new store under old code. Back up the business store before
any future deployment; deployment/merging are not part of this delivery.
