## Scope and security boundary

Business permissions are `planner`, `supervisor`, `query`. Planner and supervisor
may import/edit simulated data, calculate, verify and save server-generated
snapshots. Query can read the authorized app dataset and plans. Query export
is denied unless the membership store has an explicit `canExport: true` grant.
No factory/row/department segmentation exists in this simple baseline.

Every business API runs the official `praetorActor()` signature verifier and
current active membership lookup. Request body, localStorage, role query params,
plaintext headers and browser viewer hints never establish identity or roles.
Anonymous/services/nonmembers are denied. A removed or demoted member loses
access on the next action. No developer-role switch or fallback identity exists.
The UI renders `/api/session`; it never controls server authorization.

Identity/membership uses the official `lite-app-managed-identity` templates:
SDK >=0.4.1, stable issuer#subject keys, explicit operator-only initial admin,
invitation acceptance + approval and protected membership management. `admin`
is membership administration only and has no business read/write/confirmation
rights. The template's legacy `member` role is also denied business access.
Use explicit business roles when creating invitations. Neither is a QA role.
Membership admin can grant query exports through `POST /api/auth/members/export`
with `{key, canExport: boolean}`; query/planner cannot grant themselves roles.

## Authoritative operations

- `GET /api/state`, `/api/plans`, `/api/session`, `/api/operations`, `/api/meta`:
  active business members only; no-store responses.
- `POST /api/tables/:table`: planner/supervisor, rows + current revision + reason;
  `operation: import` logs import, other updates log edit. Full before/after
  rows preserve order quantity/due changes and deletions. Stale writes return 409.
  Expected supply imports retain the existing atomic rejection contract.
- `POST /api/calculate`: planner/supervisor; server calculates from its own
  canonical data, not client tasks/status. Snapshots are server-generated drafts.
- `POST /api/plans`: save an existing draft by id. Arbitrary client snapshots,
  verification fields and confirmation statuses are not accepted as authority.
- `POST /api/plans/:id/verify`: recomputes current supported checks on the server;
  rejects stale or legacy snapshots. Save/verify log edit with a kind field.
- `POST /api/export`: authorized export only; server generates table/plan CSV
  and commits an export record before returning the content.

Every successful supported operation records UUID, action, target, verified
actor, stored business role, server ISO time, required nonempty reason and signed
platform requestId. The same atomic JSON rename persists mutation + record;
there is no endpoint to append, alter or delete arbitrary operation records.
Client actor/time/role/requestId/audit fields are ignored. Denied authorization
logs the platform requestId. Records are local application history, not an
external tamper-proof ledger against a filesystem administrator.

## Explicit limits: not complete R7

There were no supported submit/confirm/return/release flows in the baseline.
`POST /api/plans/:id/{confirm,return,release}` first enforces supervisor role,
then returns 501 `workflow_not_supported` even for a supervisor. Planner/query
receive 403. No successful confirmation/return is claimed or fabricated in the
operation log. FR-025/030 partial-unplanned acceptance, full conflict evaluation,
resubmission/staleness workflow, immutable confirmed versions and release remain
downstream work. Do not interpret this slice as complete AC-22 or R7 acceptance.

The current main UI now uses shared server data instead of browser localStorage.
Existing browser input is deliberately not trusted or automatically uploaded:
export/import it under an authorized role when migrating. Existing server
`plans.json` snapshots are read as legacy and remain queryable/exportable;
they cannot be passed off as freshly calculated/verified/confirmed drafts.
FR-006 and six-table FR-013 isolated prototypes are retained as existing source,
not separately deployed secured product surfaces. Their outstanding UI/UAT
tracking remains open. DEC-02/tool occupancy and other existing limits remain.
FR010 issue8 is already fixed in round1; issue9 is acceptance tracking, not an
additional product defect. No issue/status/backlog mutation is part of this work.

JSON persistence assumes one application process on one local persistent mount.
Multiple instances/distributed writers, retention/pagination, per-row permission,
real SSO/browser UAT, invitation UI and production provisioning are not provided.
The official example supplies membership APIs and initializer, not a business
account/password system. No real member grants or first-admin bootstrap ran.

## Integration and activation

The branch starts at delivered FR-011 `1483f7654c4668498196fb9c44947f1b8e7e660a`,
including FR010 round1 repair, and merges delivered FR007 `9e9144214cf7a8b9041c2cc722663466d4fbba37`
(order/downtime lineage) and FR005 `e1b99835a304ee6f35ab3b478eb972dc1bbab6b9`
(BOM lineage). Reviewed FR006 and FR013 prototypes remain present through main.
Merge conflicts preserved both supply waits/conditions and personnel/downtime
behavior; server integration tests exercise their combination.

Activation is intentionally not part of this delivery. A deployment operator
must select Managed identity through the official publish UI, verify runtime
identity, confirm the exact first membership admin and canonical data directory,
then follow the skill's bootstrap procedure. No startup bootstrap, fake users,
plaintext fallback or credentials are installed. Without managed runtime the
SDK fails closed (503 unsupported); UI shows identity status and sign-in action.
Requires Node >=22.6 for the development server's type stripping; production
uses the existing bundled server. No production publish/restart/binding occurred.

## Validation

Container-only disposable validation using workspace-app-builder `app-exec.sh
--validate --mode standalone --cwd /workspace/apps/aps-fr037`: `npm ci`,
`npm test`, `npm run build`. SDK package in QA copy resolves to the workspace
injected tarball (0.4.1); only QA copy dependency paths are adapted. Official auth
example tests run alongside adversarial business API tests using temporary data
and fixture actor middleware only in test files. The real SDK is also tested for
unsigned/plaintext/forged-context rejection. TypeScript, Vite and server bundle
are built. Real managed browser/SSO UAT is not claimed.
