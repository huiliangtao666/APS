Input contract
Two registered tables appear in Data & CSV, generic queries, related-record navigation, cross-table draft editing and permissioned exports. Server and frontend definitions match. CSV shape parsing is strict; service-side full-state validation is atomic and reports file/row/field. Input is a complete cumulative set, not incremental event quantities. Reimporting an identical set returns unchanged without revision/audit growth. Duplicated task identities or task/lot consumption pairs fail rather than add together.

executionFacts / 25_模拟任务执行事实.csv:
事实编号,订单编号,工序编号,状态,开始分钟,完成分钟,观测分钟,工序完成数量,数量单位,剩余工时分钟,当前设备,暂停原因
Each order+operation has one stable fact ID. Supported states: 已开始, 部分完成, 暂停, 已完成. The fact addresses the existing unsplit whole-order operation. Start/observation/completion use the existing fixed axis, 0=2026-11-02T08:00:00+08:00. Observation cannot precede start or exceed525600. Quantities/durations are finite nonnegative decimals; fact quantities permit up to12 decimal places and magnitude1e12. Units must equal order units; no implicit conversion. Partial output is positive and below demand; started has zero output; completed means whole operation scope finished, quantity equals demand, zero remaining duration and explicit original completion later than start and no later than observation. Open work has positive explicit remaining minutes and no completion timestamp. Pause needs a reason. Current machine must match the given dependency, operation and line. A downstream started fact needs an already-completed predecessor fact ending no later than its start.

工序完成数量 is operation output, never assumed quality-approved quantity, finished goods receipt or order 已完成合格数量. It is not summed across route operations. Nonzero existing order qualified completion together with operation facts is rejected: the overlap/reconciliation basis is undecided. Completed facts do not automatically change order status, delivery quality or stock. Actual operation/remaining projections and output remainder are reported separately; plan task rows identify original facts versus simulated remaining work.

executionMaterials / 26_模拟累计耗料.csv:
记录编号,事实编号,批次编号,物料编号,累计已用数量,单位
Each fact+inventory lot has one stable cumulative record. It references an existing same-material physical simulation inventory lot and exact master unit. Expected supplies cannot become consumed inventory merely because time passed. Quantity is strictly positive. BOM mapping must be supported and sum of task/material usage cannot exceed its explicit original-start BOM demand. Overuse, scrap, returns and alternate feed basis require reconciliation, not automatic acceptance.

Explicit stock basis: inventory book quantity is BEFORE the simulated consumption ledger; reserved quantity is independent other occupancy. Available for a new plan is book minus cumulative consumption across ALL facts (including unselected orders) minus independent reservation, then the existing quality/ready/expiry policies. Totals exceeding this basis fail. Already-net stock or reservations that include that same consumption cannot be inferred: do not import them as this contract. After usage is recorded, rewriting its book/reserved/material basis is blocked to prevent deducting it again. Current quality, readiness or location can be updated as simulation input, retaining prior versions.

History and corrections
The existing verified actor/member middleware, CSRF checks, mandatory reason, stale revision guard and one atomic JSON write cover all writes. No body identity, role or client audit timestamp becomes authoritative. Planner/supervisor can edit, query members read; export still needs the stored grant. GET /api/execution exposes current facts, remaining quantities/minutes, cumulative material, original protection metadata, risk flags, fact SHA256 version, audit history and effective simulated stock. The endpoint distinguishes pre-consumption book from post-consumption balance and currently available amount.

Original fact start, task identity, machine, unit and a recorded completion cannot be overwritten or deleted. Completed facts cannot be rewritten. Forward cumulative quantity/time/material corrections and explicit remaining-time corrections preserve all previous rows in the immutable input versions and before/after actor/reason/time/request audit. Original first-record values remain queryable after later correction. Backward observation/output/material, partial→started, pause→resume/completed and overcompletion fail with reconciliation issues and do not change input, revision or audit. Changing executed demand/order status, qualified completion, production definitions or consumed stock basis also fails until there is a decided reconciliation. These are conservative blocking boundaries, not a new approved shopfloor correction policy.

Remaining-work scheduler and conservation
Original completed tasks retain their actual start/end and IDs in results; they are not scheduled again and do not allocate material again. Active work uses the explicit remaining minutes on its original current machine, starting at its observation minute. Its recorded/protected interval is never moved. Unstarted tasks cannot be placed before the latest input observation. Current execution holds are reserved before normal priority work; all-order facts and consumption remain protected even for a selected-order run. Nonselected open/paused work conservatively keeps its machine unavailable because its next release is unknown.

Paused work is unplanned with its reason and no invented resume. Active work that cannot continue at the explicit observation because of a calendar/fault, material shortage, horizon or competing execution hold remains unplanned and retains a conservative machine hold. No automatic interruption, restart, change of machine or product-quality inference is introduced. An unavailable consumed lot or overlapping fault marks affected completed/partial facts for handling; completed actual intervals still remain, while unstarted successors are blocked. Risk policy uses the frozen rule-evaluation timestamp, not Worker wall time or a future rule before it becomes effective.

For an active operation, material demand is its full supported BOM demand at the ORIGINAL start version/date minus same-task/material cumulative consumption. Operation output is not subtracted again from that demand: some material may already have been fed for output still in process. Known order-qualified completion is rejected rather than mixed with this ledger. A completed operation under MATERIAL must have full matching supported-BOM cumulative usage; otherwise allocation is blocked rather than treating its material as unused. Existing BOM scope/units/rounding restrictions remain. Rational arithmetic is exact through demand/consumption/allocation, with decimal conversion only for display.

The allocator initializes its used-lot ledger from cumulative execution materials once per calculation. It adds only remaining candidate allocations; duplicate commits stay idempotent. Calculation never writes book/reserved quantities, execution output or stock receipts. The test scenario proves120 book=40 already used+60 new-plan need+10 independent reserved+10 unallocated. Repeated calculations produce the same exact60 need and10 unallocated. A selected new order cannot reuse100 consumed by a nonselected completed order: only10 available remains and its100 demand has90 shortage. Exact0.3−0.1=0.2 and overcompletion below floating display precision are covered.

PROGRESS is now a supported scoped capability with empty parameters and documented limits. Turning it off cannot remove intrinsic protection of recorded facts. Existing stock/forecast/BOM, fixed route time, machine/calendar and Worker behavior remain. A fact-containing run cannot use minimal-r1, which omits necessary protection. Active task personnel-phase reconciliation, execution combined with batch/program, joint tooling/storage or quality/delivery semantics is deliberately blocked instead of inventing production allocations/qualified output. These combinations remain FR031/full integrated acceptance work.

Versions, Workers, trials and old plans
Current facts have a SHA256 content version. The existing immutable full-input version and execution/condition hash additionally cover stock, rules and calculation scope. Every new run freezes the facts, cumulative consumption, risks and original protection summary. Selected-order runs preserve original all-order context for validation/protection. No client-supplied context becomes authoritative. The real separate Worker receives only the frozen copy. A forward edit while a Worker runs cannot rewrite its inputs/result; completion appends to freshly read storage and preserves the newer facts. New runs use the new version. History and exported plans retain their own execution evidence, exact original input and source hashes.

Trial copies retain the original historical facts as read-only. Direct trial fact edits are rejected in both UI and API; current facts cannot be changed through a trial, retain, discard, old-plan import or restore. Recalculation and retention reject changed current fact versions and stale/edited consumed-lot conditions. A current consumed-lot quality change cannot be undone by an older trial. Retained results are independent historical snapshots, not current execution adoption. Discard keeps originals, audit/history and current inputs. Historical restore still returns409 with current input/fact hashes and explicit blockers: current simulation facts now exist, but real confirmation and full execution/restore reconciliation do not. It never restores old stock or erases current execution. No fake confirmed/released plan status is introduced.
