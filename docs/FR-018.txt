Delivered behavior
The calculation workbench selects effective formal orders on the current line, start minute, planning-end minute, stable task priority and enabled rule IDs. Forecasts, cancelled, duplicate/unknown orders, mixed/incorrect lines, unknown fields, invalid horizons and unknown sort modes cannot enter a run. MACHINE/PRECEDENCE/CALENDAR cannot be removed. Unsupported or incomplete enabled rules return field findings. Intrinsic staffing and expected-supply checks remain enforced even if optional flags are off.
All times use the existing fixed minute axis: 0 = 2026-11-02 08:00 +08:00. Choosing start minute does not shift calendars, downtime, due dates, personnel or expected-supply windows. Starts cannot precede the selected minute. A complete operation must fit at/before the selected end; otherwise it is unplanned with UNPLANNED/HORIZON, and dependent operations retain predecessor checks. No truncation, shortened duration, disabled hard constraint or claimed global infeasibility. End equality is accepted. UI asks for an explicit end (default600); the backward-compatible synchronous route may omit it to use original calendar limits.
Priority supports saved rule settings, priority-number ascending, or due-minute ascending then priority-number. Ties preserve source order. Explicit run priority overrides SORT's ordering mode for this run; the plan rule snapshot's explanation records the actual adopted ordering and its source. Saving a run does not edit the input rules table. This is the existing constructive scheduler, not optimization or a guarantee that an unplanned operation has no feasible alternative.

Immutable input contract
Admission reads one canonical server revision, clones the exact full input, derives selected execution data, freezes the exact rule rows and explicit conditions, and records a server UUID run ID, original full-input SHA256/version, independent execution/conditions SHA256, server evaluation timestamp, actor/request ID/reason and timeout. Conditions include selected IDs/line, fixed time origin, start/end, priority, rule selection and ruleEvaluationAt. Effective dates use that frozen timestamp, including after worker initialization or later edits.
The original full snapshot includes all16 supported input tables. Execution data keeps the selected orders and their dependencies/supply references plus the unchanged resource/material/configuration tables; optional rule flags reflect this run's selection. A Worker receives a structured clone of this frozen data only. It never re-reads today's business inputs. Completion re-reads current storage and appends its result, preserving intervening edits, audits, other runs and plans. New inputs can be saved during a run and another calculation opened. Tests hold a real Worker active across a time-table edit and a second run, then prove old/new actual durations30/45 and unchanged original snapshots.
GET /api/runs and /api/runs/:id expose persisted history/status. GET /api/runs/:id/inputs supplies exact originalInput, executionData and conditions, with full and execution SHA256 integrity checks. GET /api/plans/:id/inputs retains original full-input query/restore compatibility. New plans retain runId/conditions/snapshotHash alongside the existing inputVersionId and ruleSnapshot. Verification uses selected frozen order/route input and rejects missing/corrupt history; existing revision staleness protection remains. Historical Gantt resource labels use the plan's original machine snapshot. Input edits do not rewrite saved task times, old settings or run records.
The UI shows run number, original input/version hash, scope, phases, failure reasons, snapshot details and result navigation. Current-result scope/run ID is explicit. Existing permissioned rule CSV now also includes run ID, snapshot hash, exact calculation conditions and actual ordering explanation. History/input browsing retains member authorization; exports retain the existing explicit stored export grant. No body-supplied tasks, plan status, actor or rule snapshot becomes authoritative.

Truthful lifecycle and cancellation
POST /api/runs returns202 after durable snapshot admission and starts an actual separate Worker. queued means thread initialization; running is set only after a Worker progress message; completed means a result with no findings; partial means calculation completed with existing input/unplanned/conflict findings. Phase updates are persisted and audited. There is no fabricated percentage, artificial production delay or polling pretending that synchronous work remains active. Small computations may finish before the UI ever displays running.
POST /api/runs/:id/cancel requires current planner/supervisor membership, CSRF checks and reason. Cancellation atomically wins or loses against terminal result handling, terminates the actual Worker, waits for termination before replying, saves no partial plan, and records user_cancelled with actor/reason/time. Late results/error/exit messages cannot resurrect a terminal run. Already terminal cancellation returns409 run_finished; unknown runs return404. Two active Workers maximum; a third returns429. Cancelled/timed-out runs free capacity.
Server timeout30seconds includes Worker initialization/computation and terminates the thread, records timed_out/time_limit and explicitly says this is not proof of infeasibility. Worker start/error/premature exit is a distinct failed run with safe explanatory code/message; raw stack/data/secrets are not persisted. A process restart cannot resume a lost Worker, so startup records process_interrupted and leaves original input and prior saved results intact. Cancellation itself is authoritative; disconnecting the HTTP caller does not cancel work.
POST /api/calculate remains synchronous for existing consumers/tests and returns201 only with a completed/partial plan. It records a terminal run with the same frozen-input contract and never advertises a cancellable running phase. Its admission and computation execute on the main thread; this route has no cancel/timeout guarantee. The UI labels it “同步计算全部（无取消）”; the new scope selector uses the asynchronous route.
Input/selection failures before admission return400/409/422 with errors/findings and create no run, plan, audit or input mutation, preserving FR017's no-mutation-on-invalid-input contract. Those rejected requests are visible response errors, not admitted failed-run history. Admitted failures/cancellation/timeouts remain inspectable in history. A failed run does not imply no feasible schedule.
