## Input and identity

Existing originalTools/originalPersonnel records retain all source columns and literal cells (including whitespace, quotes and line breaks). New `resourceMappings` table 31 binds one source ID to one explicitly maintained runtime ID, in a typed source namespace. An ID may differ from the runtime ID (explicit alias); same names do not join. `别名` is descriptive only. A source or runtime target cannot appear twice in READY mappings. Many source aliases merging into one resource, implicit identity discovery and capacity addition are not implemented and are rejected. Original same-ID multiwindow records remain invalid; no copied people.

Source and runtime JSON pins must contain exactly the complete respective row with string values and exact literal equality, independent of JSON property order. No pin silently updates. Source types 模具/工具 may explicitly bind tools, never an inferred machine or space. Original06 binds personnelGroups; source skill text is retained exactly, group name and shift must be explicitly maintained. Personnel qualification and demand parsing use the existing CR contract; no automatic skill alias or qualification intersection.

## Supported runtime contract

`合同版本=FR013-resource-map-v1`, `映射模式=DIRECT_IDENTITY`, `范围模式=全局唯一池`, `释放策略=半开端点释放`, `时间单位=分钟`. All are explicit choices. Source sharing text must be `全工厂` or `*` (literal pin is preserved). `适用产线` explicitly names the one current configured runtime line; both current runtime and frozen checker enforce it. No cross-line combined scheduling, local scope dictionaries or per-line pool duplication.

Tool capacity is a positive safe integer **套**; personnel group eligibility is a positive safe integer **人**. Source capacity must equal runtime tool capacity / group qualification cap; source windows must equal runtime availability. Windows are integer minutes 0–525600, fixed origin 2026-11-02 08:00 +08:00, half-open `[start,end)`. Source-only decimal windows can still be stored literally; activating them is NOT_READY_CONFIG. Zero source capacity, 件/weight/labor-hour units, date conversion and multiple source windows are not supported activation combinations.

Tool claims must be explicitly declared in table23; source rows do not generate default demand, acquisition, release, units or claims. CR-DEC02-03 supports full-operation or explicit-window claims and source selection (per-claim or tool configuration), integer before/after offsets, half-open release. MOLD must actually be selected and effective in a new run, including after rule selection. Runtime tools/claims remain the authoritative executable contract, and source/target equality pins ensure its source capacity/window are adopted.

Personnel requires explicit table12 demands, skills/shift/windows and a group->enabled physical pool binding. Group eligibility limits and the pool's single global capacity both apply; two mapped groups never sum into pool capacity. P10-explicit-v2 supports sharing or group/operation mutex, explicit fixed handover-window capacity upper bounds, dependency windows or whole-operation retention. Pool source, strategy and range remain explicit. Unsupported handover addition, personal intersection or mixed candidate occupation policies are rejected by existing P10 validation. Missing actual occupation facts on executing work remain blocked by existing CR protections.

## Version, persistence, preview and adoption

NOT_READY_CONFIG is a storable draft, not an enabled runtime combination. READY requires every contract field except descriptive alias, a positive mapping version and configuration basis. Modification of the same mapping ID requires a strictly larger mapping version; reintroduction after deletion must exceed audited historical versions. Changes to pool/dependency/claim/rule configuration are additionally versioned by the global input version and complete configuration fingerprint, even if mapping pins remain unchanged.

All mutations share the service's member role, nonempty reason, origin, revision, full-proposed-state validation, execution-history and protected snapshot gates. Planner/supervisor may edit, query is read-only (export only if separately allowed). Preview uses the same gates and synchronous scheduler/checker with zero persistence. CSV preview tokens are owner/revision/state-bound; commit reparses server-owned original bytes. Any invalid enabled mapping or mixed batch writes nothing, including audit. Source-only import and incomplete drafts may be saved, but **new runs refuse all unmapped or NOT_READY source records**, instead of reporting them as adopted. This is an intentional new-run behavior change from source-only SHA31904e1; old plans remain frozen under their old contract.

UI: Data & CSV → original05/06 or table31, create pending rows from original source, maintain explicit runtime tables and JSON pins, preview source binding + joint schedule, save with reason, reload. Generic editor supports cross-table drafts. Preview is informative; commit always revalidates. Mapping and source tables export through existing query/export, current or historical plan input; table31 includes source JSON, runtime JSON, version, line, mode and units. Typed reference links connect source↔mapping↔runtime without joining names. Actual occupancy is exported via the frozen plan's resource load; it remains planned simulation, not production reservation.

New supported-mode runs freeze source records, mapping rows, runtime resources, rules, complete selected-order claims/dependencies, `originalResourceContract`, mapping version list, `originalResourceVersion` SHA256 and overall snapshotHash. Worker uses that executionData; independent checker reconstructs source/target equality, counts/windows, mapping versions, line membership and expected resource ledger without calling the scheduler/mapper. Server also protects historical input and snapshot hashes. Minimal unchecked mode cannot consume these configurations. Configurations without source mappings do not migrate old snapshots. Unknown contract versions refuse activation and independent verification.
