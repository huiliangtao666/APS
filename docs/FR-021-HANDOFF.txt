Implemented opt-in execution contract
No second engine, deployment or new app. The existing canonical server/async Worker, constructive scheduler, material allocator, input revision/snapshot machinery and role/audit paths execute the new behavior. Existing defaults leave CAPACITY/PROGRAM off and batchResources empty. R1 minimal execution always leaves material, capacity and programs unchecked.
In supported mode, simultaneously enable MATERIAL (its existing complete explicit policy), CAPACITY and PROGRAM. CAPACITY parameters must explicitly select this implemented subset:
{"装载计量基准":"BOM总投入","拆批方式":"均分","尾批处理":"报问题","合批条件":"同产品同版本同路线同程序","人员需求":"逐生产批累加"}
PROGRAM parameters:
{"兼容条件":"同产品同版本同路线同程序"}
These parameter values expose the limited implementation contract; they are not a claim that outstanding business decisions have been approved. Missing/unknown parameters, incompatible activation times or missing companion active rules block instead of silently defaulting. Rules retain their adoption/scope/parameter snapshots. Unknown rules and unsupported MAX_LAG/STORAGE still reject enabled configuration.
The new editable/importable/exportable batchResources table uses the original table15 columns:资源编号,资源类型,容量,单位,允许程序,说明. A batch declaration must reference a configured machine, use kg with positive finite capacity, list unique explicit semicolon-separated programs, and match table03 maximum exactly as a decimal value. Conflicts do not choose an arbitrary precedence. Prose notes are stored, never parsed as duration or compatibility. Fixed minutes still come from table11. Shared冷却空间 rows can be stored but their interval constraints are explicitly unchecked.
Only explicitly kg orders, remaining qualified quantity, the existing only-loss total-yield/raw-BOM calculation and a complete raw recipe are supported. Input load = remaining qualified kg / declared total yield. Every operation's chosen machine must explicitly use BOM总投入. A production batch follows the full route; derive its common allowed interval from all assigned machines (smallest max, largest min). Split into ceil(totalInput/commonMax) equal exact shares. Honor 是否允许拆分. Never use a display-rounded value or epsilon to choose a boundary. Rational numerator/denominator quantities persist with numeric display values.
Example480qualified kg /0.96 =500input kg, common max300 -> two production batches each240qualified kg/250input kg. The split does not shorten30-minute fixed operations; a120-minute configured fixed program likewise stays120. An exactly300kg input fits;300kg plus an exact tiny decimal excess splits.
Grouping is deliberately conservative: identical product, canonical BOM configuration, complete route/programs and assigned machines. Additionally EVERY machine in that common route must explicitly declare table15 batch processing, and each route program must be allowed by that machine. Otherwise production batches remain separate; absent table15 is not permission to combine ordinary machines. Different products cannot combine even if their names or a program string match. Stage-only joining/separation across different upstream routes is not implemented.
First-fit grouping follows original priority ordering and packs compatible existing production batches up to the exact common maximum. It does not manufacture extra quantity. After grouping, any group below a required minimum is explicitly blocked with UNDER_MIN_LOAD, original production quantities, per-operation resource records and uncommitted material candidate rows. There is no automatic overproduction, deletion of a remainder or configured-adjustment guess. A compatible second order may supply the missing real quantity and allow the group to run. This is constructive scheduling, not an optimizer or proof of global infeasibility.
Each production batch retains original order/product, index, exact qualified/input quantities and unique identity. Each operation receives its own resource-batch ID, machine, original min/max/basis, member identities and scheduled/unplanned status. Member task rows share the same resource cycle interval. The engine reserves that machine cycle once, while retaining per-member task IDs and predecessor links across the complete route. A rejected successor never becomes a fake scheduled task.

Material, personnel and temporal protections
FR020's exact material ledger receives each member's demand under its ORIGINAL order ID and production-task ID, at the actual candidate feed minute after calendar, machine and supply shifts. FEFO/status/expiry/effective BOM, original expected-supply references and reference/source caps remain in force. All members of one resource operation preview/commit atomically; one shortage leaves all candidates uncommitted. Prior successfully scheduled operations retain their legitimate allocations. Repeated calculations start a new plan projection and do not mutate source stock or double-debit it.
All raw demand shares sum exactly to the original order demand. Packaging keeps FR020's integer intermediate pieces/bags and damaged-share ceiling rules. If computing each production batch changes the original order's total packaging requirement, the plan explicitly blocks: cross-batch rounding allocation is undecided. It does not distribute rounding arbitrarily or increase/decrease material requirements. This check repeats at actual feed-date BOM selection, so a later effective version cannot bypass conservation. A supported integer/no-loss packaging split preserves1200total bags in the test; the original1% damaged-share480kg example would otherwise change1213to1214 and is blocked when split.
Personnel requirements are retained and accumulated separately for every production member, including skill/shift/group and participation offsets; shared labor is never inferred. Calendar continuous-window, downtime, fixed time, horizon and predecessor checks still apply to each resource operation. All enabled unsupported constraints continue to block; disabled constraints remain plainly unchecked.
Stock allocation remains plan-scoped simulation, not physical consumption, cross-plan reservations, receipt confirmation or WIP reconciliation. FR020's source unit/loss/addition/precision limitations and R5 execution gaps remain unchanged.
