Implemented behavior
- Planner or supervisor submits an independently verified server-calculated plan. Supervisor alone returns, confirms, internally releases and archives. The baseline permits the supervisor's planner actions and does not mandate a second distinct human; no unapproved separation-of-duty policy was invented.
- GET /plans/:id/review provides server-owned rule snapshots, fresh supported-rule replay, independent line/machine/precedence checks, explicit unplanned quantities/reasons, conditional supply, delivery assessment, change reasons and scope limits. GET /confirmations and /confirmations/:id support query; POST /export with confirmationId returns the frozen confirmation JSON plus separate current workflow metadata. Existing CSV/task/original-input exports remain available.
- Mutations require current input revision, workflow revision and reviewHash. Confirm/return also require the exact submissionId. Client actor, role, status, time, results or review reports cannot grant permissions or overwrite server values. Same-origin checks and reasons apply to lifecycle and export writes; malformed/conflicting Origin and cross-site requests are denied. Authentication and stored member permissions are re-read through the existing SDK/authorization layer.
- Submit/confirm require exact unplanned task IDs, explicit acceptance of partial work when present, explicit acknowledgment of conditional supply, and explicit acknowledgment of check scope. Unplanned rows preserve order/operation quantity, unit and reasons; they are not summed across operations or called satisfied orders. All currently effective formal demand must be included in the computation; a selected subset cannot silently omit the rest.
- Current input/hash, execution facts, trial revision/status, authoritative terminal run identity, original input/run hashes, plan/condition provenance, enabled-rule coverage and time-based rule activation are rechecked. Failed/cancelled/timed-out/running/copied/unchecked/stale/empty/corrupt outputs cannot be confirmed. Independent conflicts and non-understood findings block. Only enumerated, explained absence reasons on absent tasks may support partial confirmation.
- Review recomputes the saved supported scheduler output and compares every calculated result field except random presentation id/name/time, then independently checks the three implemented R1 invariants. This is NOT an independent verifier of every business constraint; that acceptance boundary remains explicit.
- Enabled delivery-rule quality, remaining-life, unknown/configuration and unsupported conditions block confirmation. Declared maximum waiting and declared but unchecked joint resources fail closed. Minimal mode and changed trial inputs differing from current authoritative data cannot be confirmed. Trial adoption/current-data reconciliation and historical restore semantics remain unsupported.
- Confirmation stores a deep immutable envelope of the plan, original input, run, submission, review and trusted supervisor decision with a SHA256 digest. Subsequent input edits preserve historical original values. Release/archive update separate workflow metadata; confirmed plan/envelope bytes remain unchanged. Every submission review is append-only retained, including returned/resubmitted records. Workflow revisions serialize repeated/concurrent decisions; mutation and audit persist together by atomic rename.
- Chinese ConfirmationPanel displays pending/history state, checks, missing demand, conditions/reasons, scope acknowledgments, role actions, audit events and immutable JSON export. Independent verification targets the selected draft. Stale/error responses refresh evidence and clear acknowledgments. Current global reason is sent by the existing authenticated API layer.
