Implemented contract
New table28 simulationEvents is available through the existing CSV import, multi-table data editor, query/export, server role guards, audit/history, calculation/run, immutable snapshot and Worker paths. Event fields: 事件编号,事件分钟,保护截止分钟,保护策略,事件类型,参数JSON,原因,需处理事实JSON. New event types: 插单,设备故障,人员缺勤,到料延期,物料状态变化. Exact JSON shapes and five tested CSV examples are in docs/samples/fr029/README.txt.

Event acceptance is an atomic input transaction: authenticate/authorize/reason/CSRF/revision; normalize requested tables; require full contemporaneous cumulative facts; validate append-only event schema and effects; apply effects to an isolated clone; check all fact transitions, source mappings, complete proposed inputs, stock and rules; preserve immutable before/after input versions and write audit rows with a shared batchID; one atomic-rename commit. Invalid effects or any invalid companion input reject before revision/history/input-version/stock mutation. The server derives affected fact IDs, rejects forged IDs, records effects and protects accepted fault/delay windows from deletion or rewrite. An identical accepted full-set reimport is unchanged with no additional effect, audit or deduction.

One batch may contain multiple events at ONE event minute. Every unfinished task must be explicitly observed at that minute; every completed observation must be no later. Events cannot precede any already recorded observation or previous event. Current output, scrap, remainder and cumulative consumption are supplied by the operator; elapsed time does not fabricate progress. UI CSV event save submits current executionFacts with the ledger; DataEditor can stage fact/event tables together. API /inputs accepts an explicit complete snapshot. Canonical full-set output contains server-computed 需处理事实JSON and must be retained for reimport. Event history is append-only, including declarations later superseded by another event.

Effects
Rush: only a NEW active formal order, explicitly supplied resource dependencies and existing masters/route/times/BOM; existing started order demand/identity remains immutable. Existing dependency rows remain unchanged; appending dependencies for new orders no longer needlessly invalidates old execution facts.
Fault: append explicit machine downtime [event,end). Affected unfinished facts require handling, retain original start/output/material and conservative indefinite machine occupancy. Completed work ending exactly at event time is preserved and not retroactively faulted by that event.
Absence: entire named group capacity unavailable [event,end). Unstarted personnel tasks wait/reallocate under existing explicit staffing rules. In-flight affected participation requires handling; partial group absence and rebasing participation offsets remain undecided.
Delay: append an immutable existing-supply delay at event time; arrival/readiness must not move earlier or precede event. Expected supply remains conditional and explicitly earmarked through supplyUses; no on-hand receipt or physical lot is manufactured. Unstarted work may wait for readiness. In-flight material shortage is not silently paused/resumed.
Material status: change an existing on-hand lot's explicitly declared simulated status. Consumed-lot references identify even completed tasks requiring handling. A later simulated good status does not erase earlier handling requirements or infer resolved product quality. Original pre-consumption stock, independent reservations and cumulative use remain unchanged.

Explicit protection policy
Only 禁止未开始任务开工 is supported: no unstarted work begins before the maximum explicitly declared cutoff; unaffected in-flight work may continue exactly from explicit observation/remainder. [event,cutoff) can be zero-length if explicitly chosen. Actual historical completed/started/material-fed facts remain protected. This is a conservative admission window, NOT a freeze of old unexecuted plan positions. Fixed planned task locks, interruption/resume/transfer/cancellation/compensation and complete recovery semantics are not implemented. Events cannot select minimal-r1 or disable effective CALENDAR; material/status delay events also require effective MATERIAL. Existing conservative execution/batch/joint/delivery restrictions remain, including unimplemented in-flight staffing rebase.
