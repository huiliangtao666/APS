## 用户要求

1. 保留横向六列和实体全名。
2. 按独立业务身份抽象主体、物料、业务凭证；供应商—物料供货条件、库存/在制/保留等通过关系表达，不照源表数量建立实体。
3. 充分说明计算、推理、换算、日期与约束关系。
4. 配置参数、冻结计算、模拟补单、源文件证据不是业务凭证，信息归入适当对象、关系和上下文。
5. 仔细研读参考HTML的“①实体与关联字段”。

## 实际解决

- v2的48张实体卡收敛为17类业务实体：客户、供应商、计划员、工厂、仓库、库存、物料、设备、班组、工装、工艺、需求、生产计划、生产任务、采购订单、补料单、库存收发单。
- 默认六列适宽、标题和字段全名不省略。属性、数据、状态、行动、关系及关系属性分区。
- 供应商—物料供货条件归R03关系属性；物料分类沿用统一身份；BOM/单位换算归物料关系。清除重复继承引用。
- 库存统一在库/在制类型，不混加来源实例。续作R19、设备保留R20、人员参与R21、工装保留R22分别绑定相关业务对象与来源字段。
- 配置、业务版本、冻结计算和证据归编制/规则/溯源上下文；模拟草稿是供应商—物料的情景供给条件R30，不创建真实采购/补料凭证。
- 52条业务关系均说明字段端点、输入、输出、基数、关联身份/范围、公式或定义、条件分支、失败/未知处理及程序依据。565项来源绑定另计，不充作业务关系。
- 关系说明包括BOM需料与收率边界、FEFO合格分配、真实投料效期、在制失败保留原锁、重量共享、固定/按量工艺历时、准备阶段、批量上限、人员/工装峰值、有向清洗、交付/保质、MOQ及补料模拟、提前期与安全库存参考量。
- 22张实际输入表337字段仍全部可追溯；工作表/JSON/API派生/概念建议分开，不虚构SQL物理表。
- 参考逐项对照保留19类对象、369项属性/数据/引用/行动、250条基础关系和125条规则（包括原公式及应用变体），解释APS归属和不直接移植的边界。
- 明确真实库存四项日事实与概念收发平衡，不从SOH差额推造流量。正式计划号/审批、补料及实物收发闭环仍标概念。组织主体不等同计划员个人。
