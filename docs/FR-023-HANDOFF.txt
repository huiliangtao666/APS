Implemented contract — explicit and default off
The existing DELIVERY rule can be enabled with * scope, effective time and exactly these parameters:
{"等待口径":"产品模拟交付等待分钟","质量口径":"显式订单模拟条件","有效期口径":"交付时剩余分钟"}
This narrowly configured simulated calculation capability does not approve new baseline/DEC semantics.
It consumes the existing product field 模拟交付等待分钟, requiring an explicit nonnegative safe integer for a deliverable assessment. Blank never means0.
New optional editable/importable table24_订单模拟交付条件.csv has columns:
订单编号,模拟质量状态,模拟质量可用时间,模拟有效期截止时间,要求剩余有效分钟
Each original order has at most one row. Foreign/duplicate rows, invalid dates or offsets, missing expiry policy and noninteger/negative remaining-life requirements fail atomic input validation. Supported simulated states: 模拟合格,模拟预计可用,待检,模拟不合格. The latter two block a deliverable conclusion. 模拟预计可用 requires a valid offset-bearing ISO timestamp. 模拟合格 may also have a later explicit ready timestamp, which is honored. These are explicit simulated order conditions, not quality releases or real execution facts.
Expiry is an explicit offset-bearing ISO cutoff or exactly 不适用. 不适用 requires remaining-life0; this is an explicit user declaration, never an inferred default. At candidate deliverability, cutoff minus candidate must be >= declared required remaining minutes. Equality passes; insufficient life leaves quantity/time unknown rather than relaxing the condition. No conversion from raw-material expiry to finished-product expiry is inferred.
Missing per-order conditions do not prevent unrelated scheduling; they make that order's deliverability unknown. Missing/disabled/future DELIVERY never silently uses current conditions. Unsupported DELIVERY parameters block. Existing minimal mode keeps DELIVERY inactive.

Result semantics
Every new canonical sync/async result saves deliveryAssessment FR023-v1 with original order IDs, task completions, batch-level completion/deliverability, order completion, order requirement, exact/decimal quantities, delay and structured evidence. The result is calculated once from frozen execution data, never recomputed when viewing history or exporting.
Task completion is the scheduled end, not an execution fact. A production batch is complete only when every configured route operation occurs exactly once with finite end, with no extra tasks. Full-order completion additionally requires all remaining quantity represented and every production batch complete. Historical completed quantity is excluded from newly scheduled quantity; it does not supply a historical delivery/quality timestamp. No remaining work therefore does not become a zero-lateness success.
For each complete batch, candidate deliverability=max(production completion+configured product wait, explicit simulated quality ready time). The candidate must also meet the explicit expiry/remaining-life test. An order's candidate time is the maximum of its batches only when ALL remaining quantity has a known candidate. It is labeled 找到的可行时间, scoped and conditional, never globally earliest or promised.
Candidates require supported mode plus MATERIAL and CAPACITY/PROGRAM batch execution, active DELIVERY and explicit quality/wait conditions. A route declaring 最大等待分钟 remains unknown because maximum-lag/upstream adjustment is unsupported. Declared tooling/space that the saved run did not check also makes deliverability unknown. Unchecked/unresolved scope is always retained, even when a supported subset gives a candidate. There is no full-business feasibility certificate.
Delayed quantity is the sum of original-order production-batch quantities whose conditional candidate is later than the requirement. This is an assessment of production quantities by the due point, not a contractual authorization to ship partial batches. Units are the order's units; current supported FR021 batching requires kg. No guessed conversion for boxes or nonkg batches. Quantity arithmetic reuses FR020 exact rationals, and exact values accompany displayed numbers.
For partial/unknown work, full-order expectedDeliverableMinute, delayedQuantity and delayMinutes are null. knownLateQuantity is only an explicit lower bound from evaluable batches; unknownDeliverableQuantity is separately retained. Missing/out-of-range requirements cannot become zero delay. A known0 delay remains status conditional-assessed with promised:false, never a delivery success/certificate. Global report and every order explicitly retain promised:false.
The fixed axis is0=2026-11-02T08:00:00+08:00; starting later does not rebase inputs. ISO outputs use UTC instants; offset-equivalent inputs produce equal times across days. This does not add configurable factory time zones or infer local midnight for expiry cutoffs.
