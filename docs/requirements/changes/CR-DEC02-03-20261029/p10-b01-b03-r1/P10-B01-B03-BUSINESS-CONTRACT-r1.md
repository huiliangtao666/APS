## 2. B03：唯一物理池与组资格人数

物理池P代表同一批可共享人员的有限人数资源，稳定标识`poolId`与显示名称分开。重命名不换身份；删除/重建不能复用旧身份改释历史。当前配置每个poolId仅一条生效容量来源C，单位“人”，有限正整数；来源记录维护人、原因、配置版本及生效范围。不得取组人数之和、最大组人数、技能数量或账本自报值代替C。同一池跨产线/工序使用时仍扣同一C，不在各范围复制容量。

人员组G保留已有组编号、人数Q、技能、单班次/可用期；**Q继续作为该组同时可提供的资格人数上限**，不是增加到池上的人数，不因映射被清空。新配置显式声明G→P；本轮一个组只映射一个池，多组可映射同池。一个物理池可以服务同任务多岗与跨任务/跨组，满足各自资格与下述总量即可。不得按同名、同技能、相同班次自动映射，也不得给每个旧组自动建立独立池来绕过共享守恒。

设分配给组g的普通岗位/交接占用总量为L_g(t)，必须同时满足：`L_g(t) <= Q_g`；`L_P(t) = Σ(g映射P) L_g(t) <= C_P`。两条都是上限。Q>C时不自动修正或增加C，实际受两者较小值限制；界面说明资格数量与物理可用人数不同。组可用期/技能/班次继续逐分配检查，池总量不是技能匹配通行证。容量修改只产生新配置，不能改写旧运行。

该模型是组级资格上限及总人数模型，不声称个人排班或具体成员互斥已经解决。若现场两个资格组只是同一批人的重叠子集，且总量+各组上限仍不足表达交集瓶颈，须明确报告“资格交集不可表达”，禁止启用该具体组合。用户若要求此类新含义，PM组织U03，另明确子池/资格交集契约；不能假装本模型检查了个人身份。**不得因此永久禁止已能表达的同池多组P10组合。**

缺少poolId、C、组映射或Q、未知/重复/失效引用、相冲突的同池容量来源均阻止新P10启用与运行；不填0/无限/独立池。允许保留清楚标识的未启用草稿，不能显示“已生效”或被Worker当成有效配置。正在使用的组/池引用删除必须整次拒绝，或在同一次显式有效映射变更中完整解决，不能留悬空引用。

## 3. B01：共用开关与岗位身份；U01待决定

推荐解释：**开关存于物理池，关闭时按任务独占该池**。任务身份沿用已冻结订单/生产批/工序任务标识，不用工序名称或订单名称替代。普通岗位和本任务交接事件的占用都归属于同一任务。任意时点的活动任务集合为O_P(t)。

- 共用开：允许多个任务/组/岗位并行，仍必须满足C、Q、技能、班次及窗口；共享绝不表示一人同时抵扣两个独立岗位。
- 共用关（推荐，**U01未批准**）：`|O_P(t)| <= 1`，即一个池同一时刻只供一个任务。该任务内部的多个独立岗位仍按人数累加，允许来自多个映射组；不是整池只许1个人，也不是只许1个岗位/组。即使只用1人，剩余容量不能给另一任务。
- 仅实际占用窗口产生独占；窗口外释放时没有独占锁。窗口外不释放则按既有全工序保留窗口占用和独占；交接延长窗口也相应延长该任务的独占时间。不得把开关解释成从任务建立到工序结束的额外整段锁。

岗位键为`(taskId, postId)`。同任务同岗位兼容窗口重叠按最大人数取包络；不同postId的同时人数相加。不同taskId即使postId同名也独立相加。跨组候选只是同一岗位的供给候选，不能把一项岗位人数重复分配到每个候选组。同岗位各行资格契约冲突沿P08/P09拒绝；不通过新池标识绕开。重叠窗口最大化先作用于**需求身份**，再分配到组与池，不能按池把所有同技能岗位max合并。

例子均为显式仿真输入：P容量2，G1/G2各Q=2且同池、资格可用，普通窗[0,30)，无其他已声明交接事件，岗位各需1。

| 输入 | 开 | 关（推荐任务独占） | 若改用其他关闭含义 |
| --- | --- | --- | --- |
| 同任务A、同组、独立岗位p1/p2 | 合法，总2 | 合法，总2、活动任务1 | “岗位独占”会判非法，改变P08/P09适用行为 |
| 同任务A、G1/G2、独立岗位p1/p2 | 合法，总2 | 合法，总2、活动任务1 | “组独占”会判非法 |
| 跨任务A/B、同组、各需1 | 合法，总2 | 并排非法；可先后排[0,30)/[30,60) | “组独占”可能仍判合法 |
| 跨任务A/B、跨组G1/G2、各需1 | 合法，总2 | 并排非法；可先后排 | 必须不能因不同groupId逃过互斥 |

仅将关闭对象设为“任务/岗位/组”的任一固定选择都会改变上述预期；现有用户确认不够选择。U01由用户经PM决定。**未决定前，共用开且显式输入完整的E01–E04链路可恢复开发，关闭语义不能宣称已验收。** 不要求为三个解释全部新增前台枚举；表中后列只是业务决定对照，不是追加功能授权。

## 4. B02：交接单位、窗口和扣算；U02待决定

推荐含义为“交接额外人数H”：交接是独立于原岗位的一项人数需求，单位“人”，H为显式正整数，不是人分钟或百分比。它仍分配到具备明确所需技能/班次的组及同一物理池。交接需求有稳定事件身份及所属任务/岗位来源，不能按每条重叠普通窗口复制，也不能被普通岗位max合并。相同事件多行只是表达窗口时按同一事件最大人数合并；不同事件相加；重复事件身份或相冲突资格拒绝。是否同一事件必须显式声明，不能猜。

这是**U02待决定的推荐**，不是擅自将“交接容量”改名后视作获批。若用户实际要“交接时段可用人数上限K”，那是供给限额而非额外需求，应使用另一公式；禁止一个未注明含义的字段在两种语义间漂移。本文不给“无交接”枚举、缺值=0或按多班自动生成交接。样例中“不含交接事件”仅表示冻结场景列明的普通岗位输入，不证明现场无需交接；要求交接但缺事件配置时禁止启用/运行。

每个交接事件明确引用**本次候选任务实际排定的开始S或结束E**为两端锚点，另填有符号整数分钟偏移。`hStart = anchorStart + deltaStart`，`hEnd = anchorEnd + deltaEnd`；锚点仅S/E，偏移按既有分钟精度与数值校验约束，必须有限且hStart<hEnd。引用结束E不等于引用某名称“下料/晚班”；随任务顺延重算两端。不得从不存在的准备/交班时长猜测。事件窗必须完整落入获分配组的实际可用期/班次及冻结运行可用边界；不能裁短交接来凑合法。负偏移不代表允许越过资源可用期。

半开窗`[hStart,hEnd)`；在hStart取得H，hEnd全部释放。普通岗只有其原参与窗口/保留窗口内计数，与交接分别释放。对于推荐额外需求口径：

`L_P(t) = 普通独立岗位分配合计 + 独立交接事件分配合计`。

**不用max(普通人数,H)**，也不把“原班人数+新班人数”再加一次。H已表示交接新增参与量，不另自动复制一套原岗位。若选供给上限口径：交接窗内应检查`普通占用 <= min(C,K)`，没有新增H需求。这两套口径不可混用；是否还需要双方不同资格、跨池调入或实际跨班交接属另外需要明确的业务范围，P06不因本设计推定完成。

可计算推荐例：P总量2，组资格Q=2、可用[0,120)，共用开。A普通岗1人[0,30)，E_A=30；交接事件h1引用A结束，两偏移-5/+5，H=1，因此交接[25,35)。B普通岗1人、固定工时10、机器独立、允许候选起点25。

| 时间片 | A普通 | A交接 | 若B从25开始 | 判据 |
| --- | ---: | ---: | ---: | --- |
| [0,25) | 1 | 0 | 0 | 总1<=2 |
| [25,30) | 1 | 1 | 1 | 总3>2，B不能25开始 |
| [30,35) | 0 | 1 | B若30开始为1 | 总2<=2，B最早可从30开始 |
| [35,40) | 0 | 0 | B为1 | 交接在35释放，B继续 |

H从1显式改为2，其他输入不变且新试算：A在[25,30)自身需1+2=3>2，移动整项A也不能解除同任务内部的相对重叠；不应伪造“推迟后可排”。A明确未排/原因“交接与原岗重叠需3、池可用2、超1”，不提交A部分账。此后是否先排独立B允许有多种合法解，不能把唯一排序作为验收标准。

只改交接窗口为[E,E+5)且H=1：A[0,30)、交接[30,35)与B[25,35)同时总量最大2，B从25开始合法。若U02改选供给上限K=1，原推荐窗口[25,35)内A占1合法，但B须等35；K从1改2时B从25合法。两种方向显然不同，这就是必须单独裁决的业务含义。所有这些是条件算术预期，产品执行状态均NOT_EXECUTED。

## 5. 保存、刷新、冻结与独立判定的共同契约

前台沿既有维护入口展示池编号/名称、总人数及唯一来源、组映射和资格人数、共用设置、交接含义/来源与分钟预览、版本/生效范围、待配置/未支持原因。中文字段标单位；预览显示“池P总2、G1资格上限1、G2资格上限1；同池合计不超过2”，不能把组2+组2显示为池4。U01/U02未决时显示“候选语义，尚未获业务决定”，不能给生效成功提示。试算mock可按本文条件离线复核，不自动替换现场配置。

计划员/主管维护；查询角色只读。按既有revision、权限及审计规则原子保存，跨表改映射和容量一次校验；拒绝时业务、审计和历史均不部分写入。保存成功后刷新/重开读取同版本；审计保留可信操作者、时间、原因、前后版本。适用范围及继承沿既有FR017契约，不能为同一池产生多套同时有效容量或静默覆盖。未来生效配置仅在有效范围进入新运行，不回填旧版本。

每次新运行冻结：契约版本及语义决定引用、池表、组表/映射、人数、共用开关、普通岗位来源与窗口、交接事件/含义/锚点/人数、技能替代、班次可用期、规则适用范围、生效版本、运行时间原点与输入指纹。字段名可由Dev确定，但业务信息必须可追溯且只有一份有效来源。本文JSON是**设计样例，不是生产schema/API**。

Worker须依据冻结输入计算需求、候选时间和分配；每次候选完整满足全部启用资源才提交。容量或互斥不足可另选时间/合法组；没有合法结果时解释具体池/组/任务/窗口/需求/可用/差额。搜索受限与数学不可行分开，不把未排等同全局无解。检查器独立从同一冻结输入重建普通岗位max/独立岗位sum、交接事件与实际窗口，再核覆盖、资格、映射、组上限、池总上限及适用互斥。不能读取当前新配置替代冻结输入，也不能相信结果账本自报poolId/人数/共享含义；不得调用分配器来复述结果。

结果账应能追溯task/post或handover事件、group、pool、来源行、人数、实际起止、所需/提供技能及替代依据。拆成多组的岗位分配量合计须恰好等于该岗位需求；同一分配不同时计普通岗和交接。删账/少人数、将同池两个组写成两个池、删交接、改关闭开关、窗口裁短、释放端点晚扣、用新配置替代旧冻结输入都必须被独立复核发现。合法配置但不合法候选计划与非法输入分别报错。

## 6. 迁移、历史、限制及解除方式

1. 旧组资料原样保留；新P10草稿明确“待池映射/总量/共用配置”。有权维护人显式输入poolId、C和映射；不推断旧组属于同池或不同池，也不自动批准仿真值。
