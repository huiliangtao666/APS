# DEC-05：质量状态、可用性与预计供给设计

## 1. 状态映射为数据

建立版本化映射`status_code/display_name/availability_class/scope/effective_interval`。`availability_class`为确定可用CONFIRMED、条件可用CONDITIONAL、不可用BLOCKED。状态中文名可以改，不通过`状态名==合格`等固定字符串决定业务结果。

同一状态在同一有效范围不能同时映射为两个分类；未知状态和缺少映射显示UNKNOWN，默认不计可用量并要求补配置。关闭映射、未支持策略与映射至BLOCKED的含义分别展示。

本mock沿用基线：可用→CONFIRMED；待检/冻结/不合格→BLOCKED；预计可用→CONDITIONAL。它是仿真配置，不是用户批准的现场状态制度，也没有新增QA在线审批/真实放行流程。

## 2. 可用数量和时点

每条库存/预计供给独立记录批次身份、物料、数量单位、账面量、既有占用、到达时间、质量最早可用时间、有效期和来源类型。不得把预计到货写成真实库存，也不能把已占用量重复分给新方案。

候选投料时点先判断：

1. 输入及单位合法，批次为该物料/适用范围。
2. 质量状态映射成立；CONDITIONAL同时要求`allow_expected_supply=true`和必需的预计时间存在。
3. `最早使用=max(到达时点,质量可用时点,其他明确可用时点)`，到货不等于已经放行。
4. 有效期覆盖实际投料点。mock采用`[最早可用,到期)`，恰好最早可用合法、恰好到期不合法。正式边界必须在策略中明确并冻结，不能由日期字符串格式隐式决定。
5. 净量按账面量减既有占用及本次已分配计算，均使用同一单位和来源版本；历史方案模拟占用与实际已采用预留的范围必须区分。

过滤后按配置的FEFO/FIFO或显式排序键分配，稳定并列键可用批次编号。排序只影响合法候选之间的选择，不能绕过质量、时间或负余额约束。

## 3. 条件供给与风险

预计供给开关关闭时不计入候选；开启后也只在预计可用时点之后计入，并逐批保留条件。状态改名不改变映射语义。

mock：UAT-10净缺LEAN0.1kg，新增模拟到货0.1kg，60分钟到达、90分钟预计可用。89分钟仍不能补齐，90分钟且允许预计供给时可以按条件补齐；关闭开关则仍缺0.1kg。这不是创建采购单、确认到货或承诺90分钟实际放行。

结果必须区分：确定供给覆盖量、条件覆盖量、净缺口；预计时点、风险原因及关联批次。条件完成/交付时间与原订单要求比较时保留依赖，不称全局最早或确定承诺。

## 4. 维护、变更与保护

- 前台配置状态映射、预计供给是否参与、时间边界和分配顺序；查询用户只读，计划员/主管按已有权限维护，保存操作者/时间/原因。
- 草稿可以修改，启用前完成映射冲突/引用/时点/单位校验。非法或过期版本保存不改变业务数据和历史方案。
- 新试算冻结映射版本、所有批次来源/占用和生效时刻；旧方案查询及导出仍显示旧状态与旧依据，不随现行状态重新解释。
- 重复导入同批次不能重复累加，预计供给后续转为库存时须有来源关联及去重契约，不能把两条来源当成双份供给；实际外部对接不在本次实现范围。

## 5. 后续验收

前台改映射/预计供给开关→刷新→新运行候选变化；未知状态、冲突映射、边界时点、负余额、引用失效、重复来源原子保护；风险数量与时间导出；旧确认方案及实际执行事实不被新配置回写。

UAT-09/10原数据及派生预计供给保留独立来源。单纯过滤器或算术检查通过不代表已经完成分配、Worker、UI或业务UAT验收。
