## 参数化共同要求

1. 业务选择进入有类型、单位、适用范围和版本的配置；中文前台表单维护，不要求普通用户填写表达式或改JSON/代码。允许的运算模式为受控枚举，不运行用户脚本。
2. 同一业务事实保持一个权威来源。既有CSV字段继续使用，新增策略通过明确外键引用，不复制两套可互相冲突的收率、可用量或资源容量。
3. 产品/产线/路线/工序配置范围、覆盖顺序和生效时间显式维护。存在两个同优先级生效配置时阻止启用，不能按读取顺序随机选择。未填写与显式0、关闭与未支持分别表达。
4. 保存草稿、校验、启用、新试算采用分开处理；不支持的模式可作为草稿但不得启用或显示检查通过。保存非法配置不改业务版本、方案或审计成功记录。
5. 新运行冻结源数据、规则、配置版本/散列、单位换算和生效时刻。后续修改仅影响新试算，旧运行、确认方案和导出仍可查原参数。
6. 数量守恒、维度一致、时间先后、已占用资源及执行事实不重复扣算是系统校验约束，不设计成“忽略错误获得可行结果”的开关。

## mock来源与使用

从原验证ZIP选择UAT-09（BOM与批次）、UAT-10（缺0.1kg）、UAT-12（五工序/容量）及UAT-14（等待/冷却）各19张业务CSV，逐字节保留。派生数据单独放置，记录父样例、改动字段及目的；不覆盖基线场景。

`mock/baseline/`是基线格式的受控副本；`mock/derived/`为明确标注的派生批次与预计供给；参数策略和`cases.json`为**设计契约数据**。新参数的应用导入器和计算实现尚未交付，不能宣称这些扩展已经可直接导入当前应用或证明应用已通过UAT。

38个数值用例是聚焦某条口径的组件数据，不是38套完整应用导入数据。用例`kind`及`inputs`明确选择该例计算模式/覆盖值；`policy-profiles.json`为独立示例策略，不隐式叠加到全部用例，例如STAGED用例不再同时采用TOTAL示例收率。4组原场景及预计供给ON/OFF两组派生场景分别有19张CSV；输入/输出和核验范围都在验收矩阵列明。

核对命令（Python标准库；无应用启动、无业务库写入）：

```bash
python3 check_mock.py
```

该命令通过只证明来源散列、CSV/JSON结构和预期数值自洽。实际前台保存、刷新、Worker、独立检查器、权限、历史保护及业务UAT必须在后续指定代码SHA验证。
