# APS交接与卡级验收规则

2026-10-29按用户确认的五角色分工及执行授权生效。旧版本和旧收件方的历史记录保留Git历史，不改写历史验收结果。唯一实施主账仍为GitHub Project2原卡，不建立新的开发/测试backlog。

## 1 角色与唯一调度入口

| 工作区 | 主责 |
|---|---|
| APS-PM | 统一调度、收妥交接、原卡/Issue及CR状态回写、同源清单、UAT依赖检查、效率观察与按需建议 |
| APS-Design | 仅业务设计，可提供业务原型、验证场景与mock，并作为需求变更提出人 |
| APS-Dev | 技术方案、实现、自测、固定版本交付和返修 |
| APS-Test | 任务级功能/规则/接口/集成/回归及修复复测，产出独立证据 |
| APS-QA | PM核对相应UAT依赖任务完成并调度后，主责UAT准备、测试、确认，在UAT中考虑独立代码审查；用户作为确认配合角色 |

PM职责已从Design迁往APS-PM。Design不再执行日常派工或实施状态维护。新增需求由Design提出，PM组织登记与批准流转；提出不等于批准。QA的修复、补证或设计缺项也由PM统一调度。

## 2 业务交付与完成通知

Design/Dev/Test/QA先保存报告和证据；Dev先普通push，再向APS-PM发送一次完成通知。queued只表示入队，completed只表示执行结束，不等于PM已处理。

通知至少包含：

- event_key为原delivery ID＋结果修订号；同结果重送不换键。
- DEV_DELIVERED / TEST_VERDICT / DESIGN_REVIEW；QA报告使用UAT_VERDICT作为正文分类，不冒充平台原生事件。
- 原FR/BR/CR/Issue与Project2唯一原卡；需求版本及本次适用断言。
- GitHub分支与40位产品SHA；设计SHA单列，无产品交付写null。
- 逐条PASS / FAIL / PARTIAL / BLOCKED / NOT_EXECUTED；本卡READY_DONE / NOT_READY建议另列。
- 可访问报告、环境/数据/配置来源、每缺陷ID及修复轮次、未验证项、下一动作与负责人。
- QA另列UAT编号、PM调度与依赖完成依据、UAT步骤/结果、独立代码审查适用范围和结论、QA确认与用户实际配合意见。

普通通知、迁移、ACK、回执和重复结果不再触发完成通知，避免循环。

## 3 PM收妥与处理

PM匹配原任务，按event_key去重，核对最新原卡与证据；先写原卡/原Issue及适用CR，再刷新同源清单，最后发一次PROCESSED回执，列原event_key、实际状态、权威链接和下一任务ID或具体等待事项。

交接分SENT、RECEIVED、PROCESSED；PROCESSED不等于Done，失败和等待也需要处理。写入仅部分成功时记录已成功动作和剩余动作，恢复时不重复成功步骤。旧投向Design的事件由PM按原event_key接续，不重新执行原业务任务，不补造处理回执。

PM收到Test结果后，可按既有持续授权直接续派下一项已有交付验证或存量验收补证，不等待普通ACK，不重复已完成同版本同范围验证。相应UAT实际依赖任务完成后由PM调度QA；QA不自行提前认领。

## 4 状态与验收对象

| 事件 | 原卡动作 |
|---|---|
| Dev实际开始已授权任务 | In progress |
| 已push并派独立Test | In review；并列保留其他未闭合范围 |
| 本卡适用已批准要求全部通过，无本范围阻断或必测未执行 | PM核对后Done，记录接受需求版本、SHA和Test证据 |
| FAIL/PARTIAL/BLOCKED或本卡仍有未满足要求 | In progress；列最小剩余动作与负责人 |
| 单个缺陷复测通过 | 关闭该缺陷；逐卡判断Done，不重开原轮次 |

共享AC仅映射本FR责任；依赖数据不等于必须等所有前置卡Done。全项目UAT、main合并、发布和仅设计CR不是通用卡级门槛；真实本卡要求仍必须验证。部分切片不冒充完整FR/CR通过。

### 分批验收与剩余项续测（2026-10-30 用户授权）

Test按固定产品SHA、批准的断言及可访问证据逐项给结论；PM可把已独立通过的子范围明确记为“该SHA/该断言PASS”，保留旧SHA通过记录。未通过或未执行的子范围另列最小缺口，并沿同一Project原卡和关联Issue派新的定向Test任务，使用不同event_key、明确输入、预期与退出条件；不得为分批验收新增第二张需求原卡，也不得重复测试已通过的同SHA同范围。整卡只有适用的已批准任务级要求全部满足时才Done。

客户真实数据、跨角色业务确认及完整业务场景可由PM列为QA主责UAT切片；前提是任务级可执行的核心功能、边界、负面行为和适用集成已取得独立Test证据。转入UAT须在原卡标出QA责任、数据/环境依赖与未覆盖风险，不能把真实产品FAIL、明确批准但未实现的产品行为或必测缺口写成PASS。场景无法自然到达、正式性能规模/规则/环境尚未批准、平台资源不足时分别记PARTIAL/BLOCKED/NOT_EXECUTED，并只针对可执行缺口续测；这些情形本身不计产品缺陷修复轮次。

QA主责UAT准备、测试和确认，用户配合；QA可给通过、退回/不通过或部分通过/待补项。未执行、必测缺口或真实阻断不得写通过；不虚构用户意见或签名。QA确认不自动批准新增范围、候选业务参数或应用发布。

## 5 阻塞、修复与授权边界

实现缺陷、设计歧义、验收证据缺口、新增需求、客户事实缺失和平台故障分别记录。缺口不伪造为产品缺陷；平台恢复重试不计新修复轮次。原缺陷最多按既有两轮规则处理，超过边界保留Issue并报告，不发第三轮。

其他尚未开始backlog新功能保持暂停，包括预派未开始项；CR-DEC02-03按既有授权实现/验收；CR-DEC04-05-06仅业务设计与mock，不派应用实现。业务默认值和新含义不由架构授权推定批准。没有可执行修复时如实等待。
