Delivered behavior
The shared capability catalog describes all18 chapter7 BR categories in20 entries, including partial implementations and unsupported configurable extensions. UI displays Chinese names, meaning/scope, parameter examples, units, ranges, current state, applicable objects, enablement and effective time. Authenticated GET /api/rules/capabilities exposes the same catalog.
Supported configurable slices: MACHINE (BR03 exclusive machine), PRECEDENCE (BR02 order/fixed duration), CALENDAR (BR05 continuous windows/downtime), LABOR (BR07 existing personnel requirements), INVENTORY (BR08 inventory availability query only), SORT (BR15 stable task sorting). Catalog membership does not claim full BR-category completion.
MACHINE, PRECEDENCE and CALENDAR are necessary for this existing scheduler: deletion, disabling, future deferral, object narrowing and unimplemented parameter keys are rejected. P0 single-line protection, configured personnel dependencies, and explicit expected-supply availability remain intrinsic execution checks even if optional configuration flags are off. Existing personnel safeguards were deliberately preserved, rather than allowing a switch to remove them. A false LABOR flag is displayed alongside the explicit intrinsic protection; it does not mean staff requirements are ignored.
Unsupported or unknown rules may be stored disabled for future configuration, always shown as unimplemented/not checked. Enabling rejects with field/row findings, including future-dated unsupported enablement. JSON storage is not evidence of rule execution. Implemented rules accept only supported parameter keys; unknown extension parameters cannot masquerade as enforced constraints.

Parameters, scope and effective time
New optional CSV/editor columns: 适用对象 and 生效时间. Legacy four-column CSV remains importable. Blank scope explicitly means all (*). All currently supported scheduling constraints apply globally; partial object restriction is rejected. INVENTORY supports * or a validated, duplicate-free comma list of configured material IDs. Its 可用质量状态 must be a nonempty list of distinct nonblank strings. Outside its scope, before its effective time or after explicit disabling, the existing default qualified-only quality guard remains. This query never allocates material or changes stock.
SORT parameter 排序方式 accepts 优先顺序 or 要求日期. Priority remains the default; due-date mode orders by configured due minute then priority, preserving input order on ties. Tests share a machine between orders and demonstrate changed actual start times, while retaining precedence, machine and calendar constraints. This is not optimization or a relaxation of feasibility constraints.
Other supported constraint parameters come from their existing referenced configuration tables; arbitrary JSON parameters such as parallel=true are rejected. LABOR enablement requires personnel requirements/groups; shared FR016 checks validate references, counts, intervals and related data. Lack of capacity or skill is a real infeasibility finding, not a reason to disable the rule.
生效时间 is blank (immediate) or a strict ISO8601 timestamp with timezone and seconds. Invalid Gregorian dates, clocks and timezone-less values are rejected. Scheduling evaluates effective time against one server-generated calculation-start timestamp, not the simulated task minute axis; the decision is frozen in the plan. Inventory queries evaluate it at the explicitly selected query as-of time. Exact boundary and equivalent-offset cases are tested.
Sample: sample-data/FR-017/16_排程规则配置.csv. It extends the existing UAT02 rule template with scope/time, inventory query and optional sorting; it is not a full-R7 input bundle.

Server boundaries and incomplete data
Both /api/inputs and /api/tables/:table reuse the existing shared full-input validation and rule assessment. Edit/import/copy/restore cannot bypass enablement checks. Newly enabling a rule also checks active-order route, positive fixed duration, unique matching machine dependency and explicit calendar coverage. Mandatory rule data tables cannot be emptied while those rules remain enabled.
For FR015 compatibility, ordinary staged input maintenance may retain incomplete per-order assignment coverage until calculation; saving such input is not a passed execution check. The rule page shows the coverage issues. Every calculation revalidates all inputs plus per-order rule coverage; incomplete or corrupt persisted inputs return422 rule_configuration_blocked with findings and make no plan/input/audit/version mutation. No missing duration/calendar/dependency is filled with zero or an implicit calendar. Valid-but-infeasible windows or personnel capacity still produce the existing plan findings and partial/unplanned tasks, with constraints left enabled.
Current server membership/roles, CSRF checks, mandatory reason, stale409, trusted actor/request ID and atomic data/audit/version persistence remain. Query members can inspect capability/history but cannot write; exports retain the existing stored grant requirement. Client tasks/settings/role/audit claims do not select actual execution settings.

History and plan-used settings
Every new calculated plan has ruleSnapshot, containing capabilityVersion FR017-v1, server timestamp, every original rule parameter/scope/effective time/flag, actual active decision, category and implemented state, explicit intrinsic checks, independent-check scope and limitations. Full input hash/version preservation from FR015 remains unchanged.
Saving new settings creates the existing immutable full-input version and rule-table before/after audit, with actor, reason, server time, batch ID and from/to versions. UI displays rule-only change history. Changing or disabling an optional rule does not rewrite old plans, their adopted settings or verification. Recalculation adopts the new settings; future-dated sorting is saved as pending and does not alter scheduling yet.
UsedRules displays the selected plan's original settings, not current rule state. A permissioned plan-rule CSV export is generated from the server plan snapshot and includes capability version, timestamp, input hash, original parameters and intrinsic/independent scope. Body-supplied settings are ignored. Historical full-input query/export and explicit restoration remain available through FR015.
Legacy plans missing a used-rule snapshot are honestly unavailable; the UI does not infer actual execution from today's or merely configured historical flags. Rule-setting export and new verification for such plans fail409 historical_rules_unavailable. Existing legacy plan/input viewing remains available where original input snapshots exist.
